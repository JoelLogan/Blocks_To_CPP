# M3 contracts: W2, the language blocks

What wave W2 builds ([next steps §3.4](../next-steps.md#34-waves)): every
block it adds or changes, the rules those blocks share, the packages that
build them in parallel worktrees, the assignment projects they turn green,
and the tests. It builds on [types.md](types.md) (types, classes, patterns,
headers, codes), [slots.md](slots.md) (typed slots, start values, menus)
and [modules.md](modules.md) (the declaration graph and the `SHARED`
field). If this file and an ADR disagree, the ADR wins. Where this file
changes something types.md or slots.md decided, §5.4 lists the change, and
the docs step makes it there. Three reviews (feasibility, completeness,
parallelism) checked it against the code at `f508fca`; §7 says what became
of each finding.

**Status (2026-10-28): done.** Every round, the integration step (§5.3) and
the docs step (§5.4) are done, and all ten assignments are green; next steps
§3.8 records the wave, what moved and what is left. Where the code differs
from this contract, the contract was corrected in place and §7.1 says why.

The owner's decisions it follows ([§3.3](../next-steps.md#33-decisions-before-m3-starts)):
M3-D2, all collections of 03 §3.7.8, the generic member block last if time;
M3-D3, a program touches only the files its blocks name; M3-D6, must-have
is what an assignment needs, the rest is if-time and moves to M4 without
sign-off when the budget is spent.

## 1. Scope

### 1.1 How to read the tables

* **Block**: the catalog ID, then the Friendly label as the catalog writes
  it (`%NAME` is a part). Every new block has `version = 1` and `lowering =
  "builtin"`; the catalog stays 1.3.0 (types.md §7).
* **Parts**, in catalog order (the order they bind in, types.md §4.3):
  `where` first, then `ref` (a `symbol_ref` field), `decl` (a
  `symbol_decl` field), `type` (a type field), `drop` (a dropdown), `tick`
  (a checkbox), `in` (a value input, with its `check` class), `stmt` (a
  statement input). A pattern follows a colon, in the grammar of types.md
  §4.2. `rep` marks a repeated part, `opt` an optional input, `= x` a
  catalog default (the shadow's tokens).
* **C++**: one line, as codegen prints it; the headers come from the
  type table (types.md §1.1 and §5.2) unless the row names them.
* **Rules**: what the analyser reports beyond the pattern checks every
  block gets (`E0301`, `E0430`); codes are in §1.11.
* **Editor**: the mutator, start values (slots.md §6), the toolbox category
  and preset. Every `ref` field has its menu kinds in
  `CATALOG_FIELD_OPTIONS` (§2.13): a block that changes the symbol lists
  `assignable` ones, a block that only reads lists `variables`.
* **Set**: *must* names the assignments that need the block (M3-D6); *if*
  is if-time, in the order the package should take it.

Indexes and sizes are `int` (types.md §1.5); every index is checked
(`.at()`), and the project option `checkedIndexing` stays `true` in W2.
The unchecked `[]` form comes with W4's context menu (§1.10).

loop; `for (auto& x : c)` over a `std::vector<bool>` does not compile
(g++ cannot bind `auto&` to its proxy items), hence the `E0301`.

Two more things belong to package A:

* **Interim type menus.** Until W4's type picker, `var.declare`'s `TYPE`
  and `func.define`'s parameter rows offer `std::vector<int>`,
  `std::vector<double>` and `std::vector<std::string>` after M2's types
  (their `types` lists, a compatible change; types.md §4.1 allows templates
  there). §2.3 adds the module's user types and a list of each (C1). Maps
  and lists of lists come from the project file and paste until W4.
* **The generic member block** is not scheduled in W2: with no
  library-pack metadata in M3, it would list only a struct's fields, which
  `type.field` already does. It moves to M4 with the `std` pack's metadata
  (M3-D2's "last, if time").

### 1.4 Input and output, math and random (`io.toml`, `math.toml`, package B)

`std::max(static_cast<double>(i), c)` with a `char` `c` does not compile,
nor does `std::max(c, i)`; the explicit template argument converts both

number, and *join* and *as text* follow it, since `b2c::to_text` copies
the console's format (`crates/b2c-codegen/src/helpers.rs`, `TO_TEXT`).
Integers are unaffected, which is what the three assignments need.

## 2. Cross-cutting rules

### 2.1 Catalog schema additions (P0)

* **Row extras.** `[[block.extra]]` gains the kinds `fields` (rows `{sym,
  name, type}`, with `types` and `type_class` as `params` has) and `values`
  (rows `{sym, name}`). An extra of kind `params`, `fields` or `values`
  must have that name. Each row declares its symbol. `b2c-model`'s
  `ROW_KEYS` (`crates/b2c-model/src/terms.rs:23`) gains `fields`, so its
  terms count for `required_format_version`; the decoder claims the
  symbol IDs of all three keys (`decode/workspace.rs:430`), and renaming,
  `outside_refs` and paste remapping (`ids.rs`) treat them as `params`.
  The editor's mirrors do the same: `apps/desktop/src/editor/sync/bdmTree.ts`
  (declarations and rename), `sync/duplicates.ts` and `sync/catalog.ts`
  (`extraDefault`).
* **A repeat counted by rows.** `repeat = { count = "params" }` (or
  `fields`) counts the rows of that extra.
* **Repeated fields.** `[[block.field]]` takes `repeat` like an input, for
  `dropdown`, `checkbox`, `type` and `symbol_decl` fields: parts `ERROR0`,
  `ERROR1`, …, each with the field's default. A repeated field has no
  pattern of its own except `field:F` on a repeated `symbol_decl`, where `F`
  is a repeated type field with the same count; it resolves to `F`'s part
  of the same index (`sig.rs`, `pattern.ts`, as `param:` and `member:` use
  the index). The mutator draws a repeated field as a member of the
  repeated group, as it does a repeated input (`blocks/layout.ts`,
  `mutators/spec.ts`, `mutators/register.ts`).
* **Joining words.** Words between the last repeated part and `…` are
  shown before each later copy of the group, as `else if` is
  (`mutators/spec.ts:244-247`); the words before the group are shown once.
  So *switch* writes `… %DO case … default …` and *try* writes `… %CATCH
  catch …`, and the second copy reads *case* and *catch* again.
* **Flag-only branches.** The *branches* mutator also takes a block with
  flag extras and gated statements but no repeated group (the file
  blocks' *if it can't be opened*); today `variadicSpec` needs `…`.
* **A type field filled from the module.** A type field whose pattern's
  class no M2 type fits (`struct`) may have `types = []`; its menu holds
  only §2.3's user types, and *choose a struct first* while there is none.
  The catalog check (`crates/b2c-catalog/src/definitions.rs:406-407`),
  catalog-gen and `B2cTypeField.fromJson`
  (`packages/blockly-ext/src/fields/type.ts:49-51`) accept it. Having no
  default, it may be absent from a block: resolve fills nothing in, and
  the analyser reports the missing choice (`E0430`).
* **Call arguments named by a struct.** The *call arguments* mutator takes
  either a `symbol_ref` naming a function, as today, or a `type` field
  naming a struct, whose fields label the parts
  (`mutators/register.ts:44-51`, `mutators/variadic.ts:311-330`). The
  symbols service gains `structFields(blockId, structId)` beside
  `functionParams` (`packages/blockly-ext/src/services.ts:97`).
* **Categories.** `Category` (`crates/b2c-catalog/src/schema.rs:90-109`)
  gains `collections`, `types`, `files` and `errors`, after `functions`, as
  03 §3.7 orders them; `catalog/toolbox.toml` gets the four categories with
  their icons (☰, ◆, ▤, ⚠) and colour tokens from P0-T, with catalog-gen,
  which refuses a category it does not know (corrected with P0-R, §7.1). A
  category with no entries is valid, and the editor does not show it.
* **`SHARED`.** The editor hides a field named `SHARED` and the label words
  before it (back to the previous part) until W3 shows it in multi-module
  projects (modules.md §7.1).

### 2.2 Struct and enum declarations

* `type.struct`'s `NAME` declares a `SymbolKind::Struct` whose `fields` are
  its rows' symbols, in row order, each a `SymbolKind::Field { owner }`
  with the row's type; `type.enum` declares `SymbolKind::Enum` with
  `SymbolKind::Enumerator { owner }` rows. Their scope is the module, like
  functions (definitions; canvas order never matters), and the scope query
  lists them with their members (types.md §2.4). The analyser declares
  them before functions, in the program's pre-pass
  (`crates/b2c-lang/src/lower/mod.rs:304-307`, C1).
* The ticks are the fields `COMPARABLE` and `PRINTABLE`, as W1 fixed
  (`crates/b2c-lang/src/lower/user_types.rs:20-22`).
* A field's type may name another struct or enum, or a list of one. A
  struct that holds itself through by-value fields is `E0420` (a
  `std::vector` of itself is fine, modules.md §4.3).
* Codegen prints types in the declaration graph's order
  (`crates/b2c-lang/src/order.rs`, new; modules.md §4), which C1 builds for
  structs, enums and functions with `E0420` and `E0421`, filling
  `ModuleFiles::source_order`; C2 adds globals and the `initialised` edges.
  A program with only functions prints exactly as before.
* The clipboard records and binds structs, enums, fields and enumerators as
  types.md §2.4 says (P0 adds the blocks to
  `crates/b2c-core-wasm/src/clipboard.rs`'s `declarations`, §2.13); C1 adds
  the recording tests W1 could not write.
* W1's formats stand after review: a printable struct prints as
  `Student{name: Ann, mark: 74}`, with text and characters unquoted and
  decimal numbers as the console writes them; an enum's `operator<<` is a
  `switch` with a final `return`.

### 2.3 Menus

* **Members** (slots.md §4.3, W1's review finding TD-3). A `members` field
  lists the members of the user type bound to its variable, from the
  preview's `SymbolInfo`s: fields in row order, enum values in row order.
  While the variable is unbound, it lists nothing and shows *choose a
  struct first* (or *an enum*). A chosen member stays shown, also when it
  stops fitting; the analyser reports `E0207`. `chosenMember`
  (`packages/blockly-ext/src/types/slots.ts`) answers for the canvas.
* **User types in type fields.** A type field lists, after its `types`, the
  module's structs and enums that its pattern's class allows (`value` takes
  both, `struct` only structs), by name, sorted, from the latest preview;
  then, where the field's class allows a list (`var.declare`, parameter
  rows, `var.global`), a list of each (`std::vector<Student>`). This holds
  until W4's picker, and it is what student_records needs (`:17`, `:36`).
  `type.new`'s `TYPE` lists only structs.
* **Definitions in reference menus.** `type.enum_value`'s `ENUM` lists enum
  definitions (kind `enums`, §2.13), not variables of an enum type.
* **Reference menus** with a pattern keep W1's rule; a `members` field
  follows it.

### 2.4 Files under M3-D3

* A program opens exactly the paths its blocks hold, as text, at run time;
  no helper opens, lists or deletes a file. A relative path is relative to
  the folder the program runs in, the project folder by default
  ([07 §7.6.2](../../spec/07-toolchain-build-run.md#762-spawning)); the
  catalog default is a plain relative name (`"data.txt"`), and the help
  text says where it is looked for. The analyser does not restrict paths (the
  program runs as the user, M3-D3); W6's threat-model review records this
  and the blocks of §1.10 that wait.
* `file.for_each_line` prints, with hidden names unique in the function
  (`b2c_file`, `b2c_file2`, as *repeat*'s counter is chosen), so nested
  loops never shadow (`-Wshadow`):

  ```cpp
  {
      std::ifstream b2c_file("poem.txt");
      if (!b2c_file) {
          std::cerr << "Cannot open poem.txt" << '\n';
          return 1;
      }
      std::string line;
      while (b2c::read_line(b2c_file, line)) {
          …
      }
  }
  ```

  Without the *if it can't be opened* part, the `if` is left out; a stream
  that failed reads no line, so the loop does not run, as with the part.
  Headers: `<fstream>`, `<string>`.
* `file.open`'s `FILE` has the type `std::ifstream` for *reading* and
  `std::ofstream` otherwise; the analyser declares it from `MODE` (the
  signature has no pattern for it). Streams are types of declared symbols
  only (ADR-0017 point 4): no parameter, field or list holds one. A stream
  closes at the end of its block's list.

### 2.5 Errors

* The catchable types are W1's four (types.md §1.1). `std::exception` (*any
  error*) catches every error the standard library throws, so W2 has no
  `catch (...)`, whose variable could not be named.
* Catch parts are tried in order; a part whose type is the same as or
  derived from an earlier part's is `W0507` (*"This part never runs: a part
  before it catches every error, so every out-of-range error too. Move this
  part above that one."*, or for the same error *"… a part before it already
  catches every out-of-range error. Remove one of the two, or choose another
  error here."*). g++ warns
  about it as well (`-Wexceptions`, on by default), so a project with it
  does not build with `-Werror`.
* A catch variable is always printed, also when no block reads it: g++
  does not warn about an unused catch parameter, even at the strict level.
* `error.message`'s `e.what()` is not a `std::string` object: codegen
  treats it as it treats quoted text (types.md §11.1), so `+` and a
  comparison make it one (`std::string(e.what()) + "!"`) and *print* writes
  it as it is.
* `error.throw` and `error.rethrow` end their path for the flow checks;
  only `std::runtime_error`, `std::invalid_argument` and `std::out_of_range`
  can be thrown, since `std::exception` takes no message.
* `E0402` uses the Lowerer's catch depth (§2.13): *throw the error again*
  is valid anywhere inside a catch part, also inside a nested *if* or loop.

### 2.6 Random and time

Spec 03 offers no seed, and W2 adds none: the helpers seed themselves from
`std::random_device` (`helpers.rs`, `RANDOM_INT`), so dice_statistics is
checked by a pattern, as the guessing game is. A seed needs one engine
shared by every random helper, which changes their generated code; it is
an M4 item. `b2c::random_real` gets its own engine the same way. *wait* is
in Control, as 03 §3.7's table puts it; the clock and the stopwatch go to
M4 (§1.10).

### 2.7 Globals and constants

* `var.global` declares a module-level variable or constant, visible in
  every function and in `main` of its module, whatever its canvas
  position. A local with its name is `W0501`. Its symbol is
  `SymbolKind::Global { is_const }` (and `SymbolInfoKind::Global`), which P0
  adds (§2.13).
* A *constant* of type `bool`, `char`, `int` or `double` whose value L10
  proves a constant expression (types.md §11.2) prints as `constexpr`;
  any other constant prints as `const`. There is no `constexpr` choice in
  W2 (the ⚙ popover is W4's), so no block can ask for `constexpr` and get
  an error.
* A constant's value folds into `Analysis::constants()` through L10's
  table, so a `const int` global is a valid `case` label in its module
  (modules.md §2's constant-expression rule; W3 applies it across
  modules).
* The declaration graph orders globals (modules.md §4.1): a global set from
  a function's result follows every global that function reads, and a
  cycle is `E0421`.
* `SHARED` is on the block from version 1 and hidden in W2.

### 2.8 Overloads and default arguments

* **Default arguments.** Each parameter row may hold a default, the input
  `DEFAULT<i>`, typed by its own parameter: `param:NAME` on the
  `symbol_decl` field of the function being defined (an extension of
  types.md §4.2 that C2 makes in `sig.rs`, `pattern.ts` and the fixture).
  The default is printed in the declaration only, the forward declaration
  in W2 and the header in W3 (ADR-0019, modules.md §3.3), so the
  definition never repeats it. A default sees the module's definitions
  (constants, globals, functions) but not the parameters, so naming one
  is `E0203`. Once a row has a default, every later row needs one
  (`E0426`). A call block takes between the required and the full number
  of arguments; the call-args mutator offers the missing ones as ⊕.
* **Overloads.** Two functions of one module may share a name when no list
  of argument types fits both, counting their default arguments and
  ignoring the pass modes (`f(int)` and `f(int&)` are one;
  `f(int)` and `f(int, int = 0)` are one, since `f(1)` fits both);
  otherwise `E0211` (*"Two functions called `area` take the same inputs
  (int, int), so a call could not tell them apart."*). The check lives in
  `declare_function` (`crates/b2c-lang/src/lower/mod.rs:515-545`), which
  today reports every repeated name.
* **Calls to an overloaded function.** A call names its function by symbol
  ID, so it never needs overload resolution. Codegen makes the intended
  function the only exact match: it casts each argument whose type is not
  exactly its parameter's (`area(static_cast<double>(w), h)`), and it
  prints quoted text and `e.what()` as `std::string("…")` (L16's form).
  Quoted text is a `const char*` in C++, and a pointer converts to `bool`
  before it converts to `std::string`, so `show("hello")` would call
  `show(bool)` without the wrapper (checked with g++ 14: no warning, prints
  `bool 1`). The analyser's resolution in 06 §6.6 is then only needed for
  typed calls (W4).

### 2.9 `switch` and `do … while`

* `switch` takes `char`, `int` and enums (`switchable`, types.md §1.3).
  Each case body is a `{ }` scope and ends with an automatic `break;`,
  left out when its last block is *return*, *stop program*, *throw*,
  *skip to next round* or *go on into the next case*. An empty case body
  prints `case 1: { break; }`.
* A label is an enum value or a constant expression of whole numbers and
  characters: a literal, a `const` with a constant value, or a calculation
  of them (`K + 1`), as C++ allows; anything else is `E0424`. Two labels
  with the same value are `E0425`: whole numbers and characters are
  compared after L10's folding (`'A'` and `65` are the same), enum values
  by their enumerator's symbol ID. P0 checks both in `consts.rs`
  (`switch_labels`), the walk that knows each item's constants in program
  order, and *check at compile time*'s `E0424` and `E0428` there too; D
  only lowers the blocks (corrected with P0-R, §7.1). L10's `ConstValue`
  (`crates/b2c-lang/src/consts.rs:58-80`, `Copy`, public) is not changed.
* A switch on an enum without a default part that misses values is
  `W0508`, and codegen adds `default: { break; }` so that `-Wswitch` never
  fires. With a default part, every path through the switch ends when
  every part ends (`E0410` holds for `to_action`); without one, a path goes
  past it.
* A *leave loop* is `E0401` when the nearest loop or switch around it is a
  switch, at any depth of *if*, *try* or file blocks between: in C++ its
  `break` would leave only the switch (checked with g++ 14: a `break` in an
  `if` in a case let the loop run on). Inside a loop inside the case it
  works as usual. *skip to next round* works, since C++'s `continue`
  reaches the loop. The Lowerer's breakable stack (§2.13) gives the
  nearest one.
* `CASE` parts start empty: at landing `VALUE` is empty, so `T` is unbound
  and no start value is known, and a connection never sets start values
  (slots.md §6). An empty label is `E0430`.
* `do … while`'s condition sees only what is visible before the block,
  not the variables its body creates. Its body runs at least once, which
  the flow checks (`W0503`) know.

### 2.10 Conversions

* `text.to_number` is `std::stoi` or `std::stod`, which read a number at
  the start of the text and ignore the rest (`12abc` is 12) and throw
  `std::invalid_argument` or `std::out_of_range`; the help text says so,
  and the Errors category holds the blocks that catch them.
* *join* and `text.as_text` take the same types and write each the same
  way, so they never disagree. Neither takes a struct, printable or not
  (`E0314`, *"Join its fields instead."*): `std::string + Student` does not
  compile, and W1's `check_printable` lets a printable struct through
  (`crates/b2c-lang/src/lower/user_types.rs:147-150`). *print* and *write
  to file* still take printable structs.
* `math.convert` (`as int`, `as double`) is unchanged.

### 2.11 The `to_string` clash

W1 generated `std::string to_string(Color)` at global scope and called it as
`::to_string(c)`, so a user function `to_string` taking that enum clashed
with it. W2 moves it into the support namespace as an overload of the
decimal helper's name: `namespace b2c { inline std::string to_text(Color
value) { switch … } }`, printed after the enum in the global `::b2c`
namespace, and *join* and *as text* call `b2c::to_text(c)`. User names
cannot start with `b2c` (`crates/b2c-ir/src/text.rs:173`), so nothing can
clash. `operator<<` stays beside the enum, where argument-dependent lookup
finds it.

The overload must stay in the global `b2c` namespace. Printed inside a
user namespace it becomes `geo::b2c`, which hides `::b2c` there, so
`b2c::to_text(x)` for a decimal stops compiling (checked with g++ 14). So
W3's item stays, reworded: once an enum lives in a module's namespace, the
overload is printed after it with the user namespace closed and reopened,
and it names the enum by its qualified name (`to_text(geo::Color)`).

### 2.12 Generated names, helpers and forms

* Hidden names (`b2c_file`) are chosen as *repeat*'s counter is: unique in
  the function, never a user name. That choice reads codegen's scan of the
  names a block mentions (§2.13), so every name a W2 block declares counts.
* A range-`for` whose body reads none of the names it declares gets
  `[[maybe_unused]]` before its declaration (`for ([[maybe_unused]] const
  auto& x : c)`): `-Wall` is always on
  (`crates/b2c-toolchain/src/command.rs:278`), and g++ 11 and 14 warn about
  an unused range-`for` variable and an unused structured binding.
* P0 writes every W2 helper in `crates/b2c-codegen/src/helpers.rs`, so
  packages only call them: `split` (two separators in a row give an empty
  part; an empty separator gives one part per character), `to_lower`,
  `to_upper` (ASCII, through `unsigned char`), `trim` (spaces and tabs at
  both ends), `replace_all` (an empty `old` changes nothing),
  `starts_with`, `ends_with` (C++17 only), `random_real` and
  `template <typename C> void remove_at(C& items, int index)`, which calls
  `items.at(…)` first, so a bad index throws as *item of* does. Each has
  its headers and its Doxygen comment, as M2's do.
* The shared collection forms stay in
  `crates/b2c-codegen/src/lower/forms.rs` (`element_at`, `size_of`,
  `range_for`, `library_object`), which A and B call and neither edits.
* Brace items (`list of`, `new … with`) are cast as slots.md §3.1 says.

### 2.13 Tables keyed by block type (P0)

Today a block that declares a name or holds statements must be added by
hand to tables in both languages; existing tests enforce some of them.
P0 fills every table for every W2 block from this file's Rules and Editor
columns, before any block exists (an entry for a block the catalog does
not have yet is never read), so packages never edit these tables. Where a
table can be read from the catalog instead (a block declares what its
`symbol_decl` fields and rows name), P0 makes it so.

* **Declarations and scopes.** For the new symbols:
  * `ITEM` (*read-only*), `KEY`, `VALUE` and `LINE` are
    `SymbolKind::LoopVariable`, visible in `BODY`;
  * a *copy* or *editable* `ITEM` is `Variable { is_const: false }`;
  * a catch `NAME<i>` is `Variable { is_const: true }`, visible in
    `CATCH<i>` only;
  * `file.open`'s `FILE` is `Variable { is_const: false }`, visible after
    the block in its list and in `FAILED`;
  * a global is the new `Global { is_const }`.

  `collect.rs` records them with `DeclKind` variants and scope paths, as
  `COUNTER_LIST` does for the `for` counter. `lower/resolve.rs` gets their
  messages.
* **Rust tables:**
  * `crates/b2c-lang/src/access.rs`: `statement_lists` and
    `is_statement_type`, which `collect.rs` and `report_parked` read
    (`tests/parked.rs` checks every statement block);
  * `crates/b2c-lang/src/lower/mod.rs`: `is_value_type` and the dispatch;
  * `crates/b2c-lang/src/query.rs`: `DEFINITION_TYPES` gains
    `type.struct`, `type.enum`, `var.global` and `program.use_header`;
  * the exhaustive matches over statements and expressions in `flow.rs`,
    `nesting.rs` and `consts.rs`;
  * `crates/b2c-core-wasm/src/clipboard.rs`: `declarations`.
* **Lowerer context.** `lower/mod.rs` and `lower/stmt.rs` gain a stack of
  breakable statements (loop or switch) and a catch depth. `jump` reports
  `E0401` from the stack (§2.9), and *throw the error again* reports
  `E0402` from the depth. Family modules push and pop through one helper.
* **Codegen scan** (`crates/b2c-codegen/src/lower/scan.rs`). Its
  `Mentions`, `Reads` and `Writes` visitors end in `_ => {}`, so a node they
  do not know would compile silently and print wrong C++. P0 gives each
  new node its arm:
  * declared names, for `Mentions`: `RangeFor`'s, the catch names,
    `FileLines`'s line, `OpenFile`'s. `FileLines`'s hidden name
    (`b2c_file`) is not a symbol, so `Mentions` cannot hold it: D picks it
    with `fresh_name` against the names in scope, as *repeat* picks its
    counter (corrected with P0-R, §7.1);
  * calls, for `Reads`, which keep a value from being hoisted:
    `RandomReal`, `ReadLine`, `ToNumber`;
  * writes, for `Writes`: `CollectionOp` to its collection, `SetField` to
    its variable, `ReadLine` to its line, `Flip` to its variable.

  Two cases show why. With g++ 11 and 14, a *for each* item named `i`
  inside a *repeat* that picked `i` fails `-Wshadow`. A *for* bound
  reading *length of* a list that the body adds to must not be hoisted:
  inlined, the loop never ends.
* **TypeScript tables:**
  * `CATALOG_FIELD_OPTIONS` (`packages/blockly-ext/src/blocks/catalog.ts`):
    every new `ref` field. `SymbolRefKinds` gains `enums`, for
    `type.enum_value`'s `ENUM`; `var.flip` takes `assignable`.
  * `MUTATOR_FOR_BLOCK` (`blocks/mutators.ts`) and `TEST_MUTATOR_FOR_BLOCK`
    (`mutators/test-fixtures.ts`): `items` for `coll.list_of` and
    `file.write`, `if` for `control.switch`, `error.try`,
    `file.for_each_line` and `file.open`, `callArgs` for `type.new`,
    `params` for `type.struct` and `type.enum`. Their tests
    (`test/blocks.test.ts:149-159`, `mutators/spec.test.ts:42-46`) check
    "every catalog block that needs one has one" until the integration
    step restores exact equality (§5.3).
  * Default names, in `apps/desktop/src/editor/toolbox/`: `names.ts`
    (`DefaultNameKind` and `BASES` gain `item`, `key`, `value`, `line`,
    `file` and `e`, `MyStruct` and `MyEnum` for `type.struct`'s and
    `type.enum`'s `NAME`, `value` for `var.global`'s `NAME`, `args` for
    `program.main`'s `ARGV`, and the row bases `field` and `Value`; and the
    kinds by block and field, `DEFAULT_NAME_KINDS`, with each kind's scope),
    which `landing.ts` and `contents.ts` read (`landing.ts` imports
    `contents.ts`, so the table cannot live in `landing.ts`), and `scope.ts`
    (names declared in a list, read from the catalog's `symbol_decl` fields).
    A repeated declaration field (*try*'s `NAME0`, …) is named by the mutator
    that creates its parts, through the `declName` hook. (Corrected by P0-T:
    the first list had no default name for the struct, enum, global and
    argument declarations, which the default-name test below needs.)
  * `apps/desktop/src/editor/services/symbols.ts`: `DECLARING`.

  A test checks that every catalog block with a `symbol_decl` field has a
  default name.
